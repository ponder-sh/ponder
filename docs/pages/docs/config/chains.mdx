# Chains [Configure chain IDs and RPC endpoints]

Use the `chains` field in `ponder.config.ts` to configure chain IDs and names, RPC endpoints, and connection options.

This guide describes each configuration option and suggests patterns for common use cases. Visit the config [API reference](/docs/api-reference/ponder/config) for more information.

## Example

This config sets up two chains: Ethereum mainnet and Optimism.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: {
      id: 1,
      rpc: process.env.PONDER_RPC_URL_1,
    },
    optimism: {
      id: 10,
      rpc: [
        process.env.PONDER_RPC_URL_10,
        "https://optimism.llamarpc.com",
      ],
    },
  },
  contracts: { /* ... */ },
});
```

## Name

Each chain must have a unique name, provided as a key to the `chains` object. The contract, account, and block interval `chain` options reference the chain name.

Within indexing functions, the `context.chain.name` property contains the chain name of the current event.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: { // [!code focus]
      id: 1,
      rpc: process.env.PONDER_RPC_URL_1,
    },
  },
  contracts: {
    Blitmap: {
      abi: BlitmapAbi,
      chain: "mainnet", // [!code focus]
      address: "0x8d04a8c79cEB0889Bdd12acdF3Fa9D207eD3Ff63",
    },
  },
});
```

## Chain ID

Use the `id` field to specify a unique [Chain ID](https://chainlist.org) for each chain. Within indexing functions, the `context.chain.id` property contains the chain ID of the current event.

The indexing engine uses `id` in the cache key for RPC responses. To avoid cache issues, make sure `id` always matches the chain ID of the configured RPC endpoint.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: {
      id: 1, // [!code focus]
      rpc: "https://eth.llamarpc.com",
    },
  },
  contracts: { /* ... */ },
});
```

:::info
  Ponder does not support chain IDs greater than JavaScript's `Number.MAX_SAFE_INTEGER` (9007199254740991).
:::

## RPC endpoints

:::warning
  Most Ponder apps require a paid RPC provider plan to avoid rate-limiting.
:::

Use the `rpc` field to provide one or more RPC endpoints for each chain.

Ponder dynamically adapts to provider rate limits to avoid 429 errors and maximize performance. Providing multiple endpoints enables intelligent load balancing and fallback logic to improve reliability.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: {
      id: 1,
      rpc: "https://eth-mainnet.g.alchemy.com/v2/...", // [!code focus]
    },
  },
  contracts: { /* ... */ },
});
```

### Custom transport

The `rpc` field also accepts a [Viem Transport](https://viem.sh/docs/clients/intro#transports), which can be useful if you need more granular control over how RPC requests are made.

```ts [ponder.config.ts]
import { createConfig } from "ponder";
import { http, fallback } from "viem"; // [!code focus]

export default createConfig({
  chains: {
    mainnet: {
      id: 1,
      rpc: fallback([ // [!code focus]
        http("https://eth-mainnet.g.alchemy.com/v2/..."), // [!code focus]
        http("https://quaint-large-card.quiknode.pro/..."), // [!code focus]
      ]), // [!code focus]
    },
  },
});
```

Here are a few common transport options.

* [`http`](https://viem.sh/docs/clients/transports/http)
* [`webSocket`](https://viem.sh/docs/clients/transports/websocket)
* [`fallback`](https://viem.sh/docs/clients/transports/fallback)
* [`loadBalance`](/docs/api-reference/ponder-utils#loadbalance)
* [`rateLimit`](/docs/api-reference/ponder-utils#ratelimit)

## WebSocket

Use the optional `ws` field to specify a WebSocket RPC endpoint for each chain.

When provided, Ponder will use WebSocket connections for realtime block subscriptions instead of polling. Websocket connections typically offer lower latency and reduced RPC usage.

With [`experimentalRangeScan`](#range-scan-experimental), `ws` carries [log notifications](#scans-triggered-by-log-notifications) instead, and the chain never subscribes to new blocks.

:::info
  If the WebSocket connection becomes unstable or fails, Ponder automatically falls back to the default polling mechanism to ensure continuous indexing.
:::

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: {
      id: 1,
      rpc: "https://eth-mainnet.g.alchemy.com/v2/...",
      ws: "wss://eth-mainnet.g.alchemy.com/v2/...", // [!code focus]
    },
  },
  contracts: { /* ... */ },
});
```

## Polling interval

The `pollingInterval` option controls how frequently (in milliseconds) the indexing engine checks for a new block in realtime. The default is `1000` (1 second).

By default, setting `pollingInterval` greater than the chain's block time **does not reduce RPC usage**. The indexing engine still fetches every block to check for reorgs. The default is suitable for most chains.

To reduce RPC usage on high-throughput chains (e.g. L2s with sub-second block times), enable [`experimentalRangeScan`](#range-scan-experimental) alongside a larger `pollingInterval`.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: {
      id: 1,
      rpc: process.env.PONDER_RPC_URL_1,
      pollingInterval: 2_000, // 2 seconds [!code focus]
    },
  },
});
```

## Range scan (experimental)

The `experimentalRangeScan` option reduces realtime RPC usage by scanning each polling interval with ranged `eth_getLogs` requests instead of fetching every block. When enabled, a `pollingInterval` larger than the chain's block time reduces RPC usage proportionally — useful for high-throughput L2 chains.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    base: {
      id: 8453,
      rpc: process.env.PONDER_RPC_URL_8453,
      pollingInterval: 5_000, // 5 seconds [!code focus]
      experimentalRangeScan: true, // [!code focus]
    },
  },
  contracts: { /* ... */ },
});
```

This option applies to chains whose indexed sources are all `log` events, including factory sources and sources without an `address`. Chains that use block, transaction, trace, or transfer sources fall back to the default per-block realtime sync, polled every `pollingInterval`. With this option, `ws` only carries log notifications (see below) and never follows every block.

Each scan requests the head block and the logs of every unfinalized block, then fetches only the blocks with matching events. When every source has a static `address`, the logs are requested by address. When a source has none, such as a factory, one request without an address covers every source's event signatures, and child addresses are matched as the scan finds them. If that request returns many logs that match no source, for example because a source's event signature is common on the chain, the scan switches to one request by address plus one without an address for the other sources.

Each scan costs about two requests no matter how many blocks elapsed, so this option only reduces RPC usage when `pollingInterval` is several times the chain's block time — roughly 4x or more. Below that it can cost *more* than the default per-block sync, which is why it is not useful on chains with slow blocks. Ponder logs a warning if it observes too few blocks per poll, counting the blocks whose `logsBloom` would make the per-block sync request logs. With [log notifications](#scans-triggered-by-log-notifications), only polls made while the subscription is down or paused are compared.

### Scans triggered by log notifications

With a [`ws`](#websocket) endpoint, the range scan subscribes to the logs it scans for (`eth_subscribe` with `logs`), rather than to every new block. A scan runs as soon as a notification for an indexed source arrives, so events are indexed moments after their block. Otherwise a heartbeat scan runs every `heartbeatInterval`, by default a third of [`reorgWindow`](#reorg-window) (60 seconds), which advances finality and picks up any log whose notification was lost.

Notifications only trigger scans: every log still comes from `eth_getLogs`, so a lost notification delays its event until the next heartbeat at most. A notified log that a scan doesn't reach, for example because the node answering `eth_getLogs` is behind, is retried within seconds. Sources with a static `address` are subscribed by address. The others, such as factory children, are subscribed by event signature, and logs from contracts the chain doesn't index trigger nothing.

Ponder scans every `pollingInterval` instead while the subscription is down, and pauses notifications when they would cost more than polling every `pollingInterval`: when they trigger more scans, or exceed two per polling interval over five heartbeats, as when a source without an `address` has a common event signature. A burst of logs pauses them only past that budget, `10 × heartbeatInterval / pollingInterval` notifications: 300 with a 60-second heartbeat and 2-second polling. The subscription resumes after a while. On chains with rare events, a `heartbeatInterval` of minutes costs fewer scans for a later sweep of lost notifications. It must be at least `pollingInterval`, and a failed scan is retried within seconds rather than at the next heartbeat.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    base: {
      id: 8453,
      rpc: process.env.PONDER_RPC_URL_8453,
      ws: process.env.PONDER_WS_URL_8453, // [!code focus]
      pollingInterval: 2_000,
      experimentalRangeScan: true, // [!code focus]
    },
  },
  contracts: { /* ... */ },
});
```

This suits providers that bill subscriptions by the bytes they deliver: a chain with few indexed events then costs little more than its heartbeat scans.

:::info
With `ordering: "omnichain"`, events on other chains wait until this chain has scanned past their timestamp, which can take up to a heartbeat while it has no events. The default `multichain` ordering doesn't wait.
:::

:::warning
This option is experimental. It changes how reorgs are detected in realtime (by comparing the block hashes and logs reported by each scan of the unfinalized window rather than tracing a contiguous chain of block hashes). The default is `false`.
:::

## Reorg window

The `reorgWindow` option controls how long Ponder retains the data required to automatically recover from a chain reorganization. The value is measured in seconds and defaults to `180` (3 minutes).

Increasing `reorgWindow` lets Ponder recover from older reorgs, but increases memory and database usage. Decreasing it reduces resource usage, but increases the chance that Ponder encounters an unrecoverable reorg and crashes with a fatal error.

The value must be an integer between `0` and `600` (10 minutes). Setting `reorgWindow` to `0` disables automatic reorg recovery by treating each block as finalized immediately. Ponder will still detect reorgs and crash with a fatal error rather than continue with inconsistent data.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: {
      id: 1,
      rpc: process.env.PONDER_RPC_URL_1,
      reorgWindow: 300, // 5 minutes [!code focus]
    },
  },
});
```

## RPC request cache

By default, Ponder [caches JSON-RPC data](/docs/api-reference/ponder/database#rpc-request-cache) in the database and reuses it between runs. Set `cacheRpcRequests: false` to disable the cache for a chain. Ponder then does not read or write these items in the database, and fetches them again each time it starts:

- Block data (blocks, logs, transactions, transaction receipts, and traces)
- Factory child addresses
- `context.client` requests

Disable the cache for a development node like Anvil, where the chain can reset, or for a node you run yourself, where fetching data again is cheaper than storing it in the database. [Read more](/docs/guides/foundry) about indexing Anvil.

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    anvil: {
      id: 31337,
      rpc: "http://127.0.0.1:8545",
      cacheRpcRequests: false, // [!code focus]
    },
  },
});
```

## `eth_getLogs` block range

Ponder does its best to automatically determine the maximum block range for JSON-RPC requests with the `eth_getLogs` method. When this comes up short, you can set a manual limit with `ethGetLogsBlockRange` option. 

```ts [ponder.config.ts]
import { createConfig } from "ponder";

export default createConfig({
  chains: {
    mainnet: {
      id: 1,
      rpc: "https://eth-mainnet.g.alchemy.com/v2/...",
      ethGetLogsBlockRange: 1000, // [!code focus]
    },
  },
});
```
